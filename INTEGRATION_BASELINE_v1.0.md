# M.A.R.C.U.S. Integration Baseline v1.0

**Status:** Architectural baseline (normative for integration)  
**Version:** 1.0  
**Effective:** 2026-11-15  
**Scope:** The three repositories listed below, and no others.

This document is the system-level contract for M.A.R.C.U.S. It distinguishes agreed architecture and integration requirements from functionality that has actually been implemented. A contract in this document is not evidence that a component is implemented, tested, or production-ready.

## 1. Governing decisions

1. M.A.R.C.U.S. is one distributed software system composed of independently verifiable repositories.
2. The system boundary is closed to the three repositories in §2. No fourth repository, service, or required infrastructure may be introduced without an approved Architecture Decision Record (ADR).
3. Repository responsibilities, schemas, interfaces, dependency constraints, verification, and release gates in this document are normative for integration.
4. Internal implementation remains independently owned by each repository, provided it meets its published contract.
5. A component or release must not be described as production-ready unless it passes the applicable verification and release gates in §8.
6. Repository names, default branches, and sizes below are an inventory snapshot, not a measure of capability. Existing contents are sparse; the contracts below establish intended behavior, not present implementation.

## 3. Canonical conventions

- Encoding: UTF-8 JSON. Object keys are case-sensitive `lower_snake_case`.
- Timestamps: RFC 3339 UTC strings (`...Z`).
- Identifiers: opaque strings. `request_id` is generated by the caller and preserved across all component calls; components must not replace it.
- Extensibility: consumers must ignore unknown object properties. Producers must not change the meaning or type of a field in a compatible minor release.
- Required fields are explicitly marked below. Optional fields may be absent; `null` is not a substitute for an absent value unless stated.
- Errors are explicit result values (see §5), never silently converted to success or empty data.
- Audio bytes are passed by an implementation-specific local mechanism or reference. This baseline does not mandate storage, cloud services, a broker, or a network protocol.

## 4. Canonical schemas and component interfaces

The following JSON shapes are the language-neutral v1.0 contract. They are illustrative canonical structures; implementations may use different internal types. Any transport adapter must preserve their meaning.

### 4.1 Analysis request

The Meta Engine accepts an `AnalysisRequest` and forwards the same `request_id` and audio identity to its components.

```json
{
  "schema_version": "1.0",
  "request_id": "opaque-caller-generated-id",
  "audio": {
    "media_type": "audio/wav",
    "content_sha256": "64 lowercase hexadecimal characters",
    "source_ref": "optional implementation-local reference"
  },
  "requested_operations": ["musical_fingerprint", "dsra_analysis"],
  "options": {}
}
```

Required: `schema_version`, `request_id`, `audio.media_type`, `audio.content_sha256`, and `requested_operations`. `source_ref` is optional and must not be exposed in logs or outputs if it contains credentials or private data. `options` defaults to an empty object. Only declared operations are requested; unsupported operations produce a structured error, not an implicit fallback.

The caller is responsible for making the audio available to the implementation. The digest identifies the exact input bytes; components must not claim to have analyzed bytes that do not match it.

### 4.2 Fingerprint component interface

**Operation:** `generate_fingerprint(AnalysisRequest audio identity and input)` → `FingerprintResult`.

```json
{
  "schema_version": "1.0",
  "request_id": "opaque-caller-generated-id",
  "status": "succeeded",
  "input_content_sha256": "same digest as request.audio.content_sha256",
  "fingerprint": {
    "format": "implementation-defined stable format identifier",
    "value": "implementation-defined serialized fingerprint",
    "algorithm": "stable algorithm identifier",
    "algorithm_version": "version string"
  },
  "warnings": []
}
```

`fingerprint` is required on success and absent on failure. `format`, `value`, `algorithm`, and `algorithm_version` are required on success. The producer documents the meaning and stability guarantees of its format; the Meta Engine treats the value as opaque and does not recompute or reinterpret it. The same bytes and algorithm version must produce the same fingerprint, unless the producer documents a deterministic configuration that was not held constant—in that case that configuration must be represented in versioned metadata. No accuracy or matching-quality threshold is implied by this contract.

### 4.3 DSRA component interface

**Operation:** `analyze(AnalysisRequest audio identity and requested DSRA operation)` → `DsraResult`.

```json
{
  "schema_version": "1.0",
  "request_id": "opaque-caller-generated-id",
  "status": "succeeded",
  "input_content_sha256": "same digest as request.audio.content_sha256",
  "result": {
    "format": "stable DSRA result format identifier",
    "data": {}
  },
  "warnings": []
}
```

`result` is required on success and absent on failure. DSRA owns and must document the schema and semantics of `result.data`; this baseline does not invent DSRA-specific findings or scores. A DSRA schema change that affects consumers requires a versioned compatibility decision and corresponding contract tests.

### 4.4 Aggregate response

The Meta Engine returns one `AnalysisResponse` for the request, even if an individual requested operation fails.

```json
{
  "schema_version": "1.0",
  "request_id": "opaque-caller-generated-id",
  "status": "succeeded|partial|failed",
  "input_content_sha256": "request audio digest",
  "components": {
    "musical_fingerprint": { "status": "succeeded|failed|not_requested", "result": {}, "error": null },
    "dsra_analysis": { "status": "succeeded|failed|not_requested", "result": {}, "error": null }
  },
  "warnings": []
}
```

For each component, exactly one status applies. `result` is present only for `succeeded`; `error` is present only for `failed`; neither is required for `not_requested`. Overall status is `succeeded` when all requested operations succeed, `partial` when at least one requested operation succeeds and at least one fails, and `failed` when none of the requested operations succeeds. A request with no supported requested operations is invalid and returns a request-level error. Results must retain their component schema/version and must not be silently rewritten by the Meta Engine.

### 4.5 Error envelope

```json
{
  "code": "stable_machine_readable_code",
  "message": "safe human-readable summary",
  "retryable": false,
  "details": {}
}
```

`code`, `message`, and `retryable` are required. `details` is optional and must not contain secrets, raw audio, or sensitive source references. Component errors remain attributable to their component in the aggregate response. Error codes and retry semantics must be documented by each producer; consumers must not infer retryability from message text.

## 5. Dependency and compatibility rules

1. Allowed logical dependency direction: Meta Engine → Musical Fingerprint and Meta Engine → DSRA. The two component repositories do not depend on each other. Neither component depends on the Meta Engine.
2. No runtime dependency on a fourth repository or externally operated service is part of this baseline. New requirements of that kind need an ADR before implementation.
3. Integrations use the published contracts, not another repository's private modules, source tree, database, or undocumented behavior.
4. Each repository owns its implementation and its contract tests. Any cross-repository contract change must be coordinated with affected repositories and merged/released compatibly; do not make a consumer depend on an unreleased producer change.
5. Schema version `1.0` permits additive optional fields that follow §3. Removing or renaming fields, changing requiredness or type, changing semantics, or breaking result compatibility requires a new major contract version and ADR.
6. Component and aggregate outputs carry `request_id` and the input digest. A digest mismatch is a failed integrity check, not a warning-only success.
7. Release notes identify the exact dependency versions or immutable revisions used for verification. A mutable branch name alone is not a release pin.

## 6. Failure, privacy, and deterministic behavior

- Validate request shape and supported operation names before invoking components.
- A component failure must not erase a successful independent component result; represent the outcome as partial when appropriate.
- Do not retry non-retryable errors. Retry policy, if added, must be bounded, documented, and covered by tests; no distributed queue or retry service is required by v1.0.
- Never log raw audio, credentials, or sensitive `source_ref` data. Logs should correlate by `request_id` and use safe error codes.
- Fingerprint generation is deterministic for the same input and declared algorithm/configuration. DSRA must document any nondeterministic behavior and its causes; the Meta Engine must preserve provenance and not assert determinism on DSRA's behalf.
- Resource limits, supported audio formats, and retention behavior must be documented by the component that imposes them. This baseline does not establish a production workload or service-level objective.

## 7. Verification requirements

Each repository must provide reproducible, repository-local verification and publish the commands needed to run it. At minimum:

**Meta Engine**
- Unit tests for request validation, dispatch, correlation IDs/digests, aggregation status rules, error mapping, and unsupported operations.
- Contract tests using successful, failed, and not-requested component fixtures, including partial success.
- Integration test proving a request traverses both component interfaces and returns one correlated aggregate response (using real components where available, otherwise clearly identified test doubles).

**Musical Fingerprint**
- Unit tests for valid and invalid input, stable output structure, digest propagation, errors, and determinism for fixed bytes/configuration/version.
- Golden-vector test fixtures with documented fixture provenance and expected algorithm/version metadata.
- Contract test validating v1.0 `FingerprintResult` success and failure shapes.

**DSRA**
- Unit tests for its documented analysis behavior, input validation, error cases, and output schema.
- Contract tests validating v1.0 `DsraResult` success and failure shapes, including request/digest propagation.
- Any data-dependent test must declare its fixture/source and must not rely on an undocumented live external service.

**System-wide**
- Schema/contract compatibility checks run against the exact component revisions being released.
- Negative tests cover malformed requests, digest mismatch, component failure, and missing required output fields.
- Tests must be repeatable from documented instructions. A passing test suite is evidence only for the tested revision and scope; it is not by itself proof of production readiness.

## 8. Release acceptance criteria

A component release is accepted for integration only when all of the following hold:

1. Its owner documents the implemented responsibility, supported inputs/outputs, limitations, and verification command.
2. Its repository-local tests pass on the release revision, including its v1.0 contract tests.
3. It has no known unresolved critical failure in the declared release scope; known limitations are recorded rather than hidden.
4. The release identifies an immutable revision and a compatible schema/contract version.
5. The consuming Meta Engine passes its contract and integration tests against that exact revision.

A M.A.R.C.U.S. system release is accepted only when:

1. All three repositories are represented by immutable revisions in a release record.
2. The dependency direction and closed three-repository boundary are respected.
3. All repository-local and system-wide verification in §7 passes for those revisions.
4. Success, partial success, failure, digest integrity, and error behavior match §§4–6.
5. Documentation identifies implementation gaps, unsupported inputs, operational assumptions, and known limitations.
6. No component is labeled production-ready without separate evidence that its production deployment, security, reliability, performance, and operational requirements have been defined and met. Such requirements are outside this baseline and require an explicit ADR or release policy.

## 9. Change control and ADRs

An ADR is required before changing the three-repository boundary, adding infrastructure or a repository dependency, reversing the dependency direction, changing a schema incompatibly, or materially changing repository responsibilities. An ADR records context, decision, alternatives, consequences, owner, and affected repository contracts. Until approved, this baseline remains authoritative.

Compatible corrections and clarifications may be made as a minor revision with review from affected repository owners. Record the baseline version used by every system release.

## 10. Explicitly not claimed by v1.0

This baseline does not claim that any interface or schema is already implemented, that the repositories currently pass these tests, that DSRA has a particular expanded name or result ontology, that fingerprint quality meets a threshold, or that the system is deployable or production-ready. Those claims require implementation evidence and release acceptance under this document.
